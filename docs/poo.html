8  Programmation orientée objet en R

Jusqu’à maintenant, nous avons principalement programmé en utilisant des fonctions.

Nous écrivons une fonction :

moyenne <- function(x) {
  sum(x) / length(x)
}

puis nous lui fournissons des objets :

moyenne(c(1, 2, 3))

Cette façon de travailler est très naturelle en R. En fait, la programmation fonctionnelle occupe une place particulièrement importante dans le langage.

Il existe cependant une autre façon d’organiser un programme : la programmation orientée objet, ou POO.

L’idée générale consiste à associer certains objets à une classe, puis à définir des comportements adaptés à cette classe.

Cette approche devient particulièrement intéressante lorsque nos fonctions retournent des résultats complexes que nous voulons :

  • organiser;
  • manipuler;
  • afficher;
  • réutiliser;
  • transmettre à d’autres fonctions.

C’est exactement ce qui se produit avec plusieurs fonctions statistiques classiques de R.

8.1 Programmation fonctionnelle et programmation orientée objet

Considérons un modèle linéaire :

fit <- lm(
  mpg ~ wt + hp,
  data = mtcars
)

La fonction lm() retourne beaucoup plus qu’un simple vecteur de coefficients.

class(fit)

retourne :

[1] "lm"

L’objet fit contient plusieurs informations :

names(fit)

par exemple :

coefficients
residuals
effects
fitted.values
rank
...

Nous pouvons ensuite utiliser le même objet avec différentes fonctions :

print(fit)

summary(fit)

predict(fit)

plot(fit)

Chacune de ces fonctions comprend comment interagir avec un objet de classe "lm".

C’est l’une des idées principales de la programmation orientée objet en R.

                    objet fit
                    classe "lm"
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       print()       predict()       plot()
          │             │             │
          ▼             ▼             ▼
     affichage       prédiction    diagnostic
     approprié       appropriée     approprié

Nous pouvons donc créer un objet relativement riche et ensuite lui associer plusieurs comportements.

8.2 Pourquoi utiliser la programmation orientée objet?

Tout d’abord, comprennons que nous pourrions faire un cours de 45 heures sur la POO, ici nous ne ferrons qu’un survol très rapide d’une version très spécifique de la POO en R. L’objectif est de mettre au point une petit rampe de lancement et vous pourrez voler de vous même si nécessaire par la suite.

L’un des principaux intérêts de la POO est le polymorphisme.

Le polymorphisme permet d’utiliser une même interface avec plusieurs types d’objets.

Par exemple :

print(x)

peut produire des résultats complètement différents selon la nature de x.

Même chose pour :

summary(x)

ou :

plot(x)

Considérons :

x <- 1:10

summary(x)

puis :

f <- factor(
  c("A", "A", "B", "C")
)

summary(f)

Nous utilisons exactement la même commande :

summary(...)

mais le comportement est adapté à la classe de l’objet.

Nous pourrions évidemment imaginer une énorme fonction contenant :

if (...) {

} else if (...) {

} else if (...) {

}

pour traiter tous les types d’objets possibles.

Mais cette approche deviendrait rapidement difficile à maintenir et, surtout, difficile à étendre.

La POO permet plutôt de séparer :

l'interface
    ↓
summary()

de

l'implantation
    ↓
que doit faire summary()
pour cette classe particulière?

Cette séparation devient particulièrement importante lors du développement de librairies.

8.3 Quelques concepts fondamentaux

Avant d’étudier les différents systèmes de POO disponibles dans R, introduisons quelques termes.

Objet

Un objet contient des données.

Par exemple :

x <- c(2, 4, 6)

crée un objet.

Cependant, il faut faire attention à la terminologie.

On dit souvent que :

Tout est un objet dans R.

C’est vrai au sens général : les vecteurs, fonctions, matrices, listes, environnements, etc. sont tous des objets manipulables dans R.

Mais cela ne signifie pas que tous ces objets participent nécessairement à un système de programmation orientée objet.

Par exemple :

x <- c(1, 2, 3)

est évidemment un objet R, mais ce n’est pas nécessairement un objet S3, S4, R6 ou S7.

Il faut donc distinguer :

objet R

et :

objet participant à un système de POO

Classe

Une classe décrit le type conceptuel d’un objet dans un système orienté objet.

Par exemple :

fit <- lm(
  mpg ~ wt,
  data = mtcars
)

class(fit)

retourne :

[1] "lm"

Nous pouvons donc dire que :

fit

est un objet de classe :

"lm"

La classe permet notamment à R de déterminer quels comportements utiliser avec cet objet.

Méthode

Une méthode est une fonction conçue pour fonctionner avec une classe particulière.

Par exemple, il existe une méthode spécialement conçue pour afficher les objets "lm" :

print.lm()

Il existe également une méthode permettant de faire des prédictions :

predict.lm()

et plusieurs méthodes permettant de tracer des graphiques appropriés.

Une méthode répond donc essentiellement à la question :

Que doit faire cette opération lorsqu’elle reçoit un objet de cette classe?

Générique

Une fonction comme :

predict()

n’effectue pas elle-même toutes les prédictions possibles.

C’est une fonction générique.

Son rôle principal est de déterminer la classe de l’objet et de trouver la méthode appropriée.

Par exemple :

predict(fit)

avec :

class(fit)
# "lm"

conduit R à utiliser une méthode appropriée à la classe "lm".

Conceptuellement :

predict(fit)
     │
     ▼
quelle est la classe de fit?
     │
     ▼
    "lm"
     │
     ▼
predict.lm()

Le processus permettant de choisir la méthode appropriée s’appelle le method dispatch, ou la répartition des méthodes.

Trois concepts à ne pas confondre 
Classe
    ↓
Quel type d'objet avons-nous?


Générique
    ↓
Quelle opération voulons-nous effectuer?


Méthode
    ↓
Comment cette opération doit-elle être effectuée
pour cette classe particulière?

8.4 POO fonctionnelle

Les systèmes S3 et S4 utilisent principalement une forme de programmation orientée objet appelée POO fonctionnelle.

Dans ce paradigme, nous appelons une fonction :

predict(objet)

et R détermine ensuite quelle implantation utiliser.

La fonction générique occupe donc le rôle central :

             predict()
                 │
       ┌─────────┼──────────┐
       ▼         ▼          ▼
 predict.lm()   ...     autre méthode

Du point de vue de l’utilisateur, cela ressemble donc toujours beaucoup à de la programmation fonctionnelle traditionnelle :

fonction(objet)

Cette approche est très caractéristique de R.

8.5 POO encapsulée

Dans plusieurs autres langages orientés objet, les méthodes sont plutôt associées directement aux objets.

On retrouve alors une syntaxe conceptuellement semblable à :

objet.methode()

Par exemple :

modele.predict()

plutôt que :

predict(modele)

Dans cette forme de POO, l’objet regroupe davantage :

données
+
comportements

On parle alors de POO encapsulée.

Le système R6 adopte principalement cette philosophie.

Nous pouvons donc distinguer grossièrement :

POO fonctionnelle
────────────────────────

predict(modele)

S3
S4
S7


POO encapsulée
────────────────────────

modele$predict()

R6

Cette distinction explique pourquoi la POO en R peut sembler un peu inhabituelle pour une personne provenant d’un langage comme Python, Java ou C++.

8.6 Héritage

Les classes peuvent également être organisées de manière hiérarchique.

Une classe peut être une version spécialisée d’une autre classe.

On parle alors d’héritage.

Par exemple, dans R, un modèle linéaire généralisé possède notamment les classes :

fit <- glm(
  am ~ wt,
  data = mtcars,
  family = binomial()
)

class(fit)

qui retourne :

[1] "glm" "lm"

L’objet est donc d’abord considéré comme un objet "glm", mais il peut également hériter de comportements associés à "lm".

Conceptuellement :

lm
│
└── glm

Si une méthode spécialisée existe pour "glm", celle-ci peut être utilisée.

Sinon, R peut chercher une méthode définie pour une classe parente.

L’héritage permet donc de réutiliser des comportements déjà définis.

Hériter de méthodes

L’héritage ne signifie pas seulement qu’un objet possède plusieurs étiquettes.

L’intérêt principal est qu’une classe plus spécialisée peut hériter des méthodes définies pour une classe plus générale.

Nous reviendrons en détail sur ce mécanisme lorsque nous étudierons S3.

8.7 Plusieurs systèmes de POO dans R

Une particularité importante de R est qu’il ne possède pas un seul système de programmation orientée objet.

Plusieurs systèmes coexistent.

Les principaux que nous rencontrerons sont :

S3
S4
R6
S7

Ils répondent à des besoins différents et ne possèdent pas tous la même philosophie.

8.8 S3

S3 est le système de programmation orientée objet le plus ancien et le plus simple que nous étudierons.

Il est également profondément intégré à R.

On retrouve S3 derrière plusieurs objets que nous utilisons quotidiennement :

factor
data.frame
lm
glm
Date
...

S3 est volontairement peu formel.

Une classe S3 repose essentiellement sur l’utilisation d’un attribut :

class

et sur certaines conventions concernant le nom des méthodes.

Cette simplicité rend S3 :

  • facile à créer;
  • facile à étendre;
  • très flexible;
  • particulièrement bien adapté à de nombreuses librairies statistiques.

Cette flexibilité vient cependant avec relativement peu de mécanismes permettant d’empêcher le programmeur de construire un objet incohérent.

S3 repose donc beaucoup sur les conventions.

Pour notre projet Ridge, S3 sera particulièrement naturel.

Nous voulons qu’une fonction :

ridge(...)

retourne un objet contenant plusieurs informations :

coefficients
lambda sélectionné
grille de lambda
erreurs de validation croisée
formule
...

puis permettre :

print(fit)

predict(fit)

plot(fit)

Notre objet pourra donc avoir la classe :

"ridge"

et posséder des méthodes :

print.ridge()

predict.ridge()

plot.ridge()

Nous consacrerons donc la plus grande partie de cette séance à S3.

8.9 S4

S4 peut être vu comme un système plus formel et rigoureux que S3.

Avec S4, les classes sont définies explicitement et la structure des objets est davantage contrôlée.

On peut notamment spécifier :

  • les composantes qu’un objet doit contenir;
  • le type de chacune de ces composantes;
  • certaines conditions nécessaires pour qu’un objet soit valide;
  • des relations d’héritage formelles.

Cette rigueur nécessite davantage de travail lors de la conception.

En échange, S4 offre davantage de garanties sur la structure des objets.

Il devient particulièrement intéressant pour des systèmes logiciels :

  • relativement grands;
  • maintenus sur une longue période;
  • possédant plusieurs classes reliées;
  • développés par plusieurs programmeurs.

S4 est notamment très présent dans l’écosystème Bioconductor.

Dans ce cours, nous allons principalement chercher à comprendre et reconnaître S4, plutôt qu’à développer une architecture complexe basée sur ce système.

8.10 R6

R6 adopte une philosophie assez différente de S3 et S4.

Il permet de créer des objets dont les méthodes sont associées directement à l’objet.

On peut donc obtenir une syntaxe ressemblant à :

objet$methode()

R6 permet également de créer des objets mutables.

Cela signifie qu’une méthode peut modifier directement l’objet plutôt que de toujours créer une nouvelle copie.

Cette propriété est particulièrement utile lorsque nous voulons représenter un objet qui possède une existence ou un état indépendant de R.

Par exemple :

connexion à une base de données
session web
API
fichier externe
état d'une application

Dans ces situations, l’objet R peut agir comme une interface vers une ressource externe dont l’état évolue.

R6 est donc particulièrement utile pour certains types de développement logiciel, mais il sera moins central pour notre projet statistique Ridge.

Nous n’en ferons qu’un bref survol.

8.11 S7

S7 est un système de programmation orientée objet beaucoup plus récent.

Il a été conçu pour tirer des leçons des forces et des faiblesses de S3 et S4.

On peut grossièrement voir S7 comme une tentative de conserver plusieurs qualités de S3 :

  • une interface relativement naturelle;
  • une POO fonctionnelle;
  • l’utilisation de fonctions génériques;

tout en ajoutant davantage de structure et de garanties, comme dans S4.

S7 permet notamment de définir explicitement :

  • des classes;
  • des propriétés;
  • des validateurs;
  • des constructeurs;
  • des génériques;
  • des méthodes;
  • des relations d’héritage.

Une différence conceptuelle importante est que les classes S7 sont elles-mêmes des objets explicitement définis.

S7 possède également un système formel d’héritage permettant à une classe enfant d’hériter des méthodes de sa classe parente.

L’objectif à long terme est donc de proposer un système moderne qui puisse éventuellement jouer une partie du rôle actuellement partagé entre S3 et S4.

S7 demeure toutefois beaucoup plus récent que S3 et S4.

Pour cette raison, nous allons surtout chercher à comprendre :

  1. pourquoi un nouveau système a été proposé;
  2. quelles améliorations il apporte;
  3. comment sa philosophie se compare à S3 et S4.

8.12 Résumé des principaux systèmes

Nous pouvons grossièrement comparer les quatre systèmes de la façon suivante :

Système Style Principale qualité Principale utilisation dans ce cours
S3 POO fonctionnelle Simple et flexible Approfondi
S4 POO fonctionnelle Formel et rigoureux Survol
R6 POO encapsulée Objets mutables Bref survol
S7 POO fonctionnelle Structure moderne combinant plusieurs idées de S3 et S4 Survol

Il ne faut donc pas chercher un système qui serait toujours « meilleur » que les autres.

Le choix dépend notamment :

  • de la complexité de la librairie;
  • de la durée de vie prévue du projet;
  • du nombre de développeurs;
  • du niveau de validation souhaité;
  • de la nécessité ou non d’avoir des objets mutables;
  • de l’écosystème dans lequel la librairie doit s’intégrer.

Dans le contexte de ce cours, nous n’allons que discuter longuement dy système S3 et faire un léger survol des système S4 et S7.

8.13 S3 : un premier système de programmation orientée objet

Nous allons maintenant nous concentrer sur S3, le système de programmation orientée objet le plus simple et le plus utilisé dans R.

L’objectif n’est pas d’étudier toutes les subtilités de S3. Nous voulons plutôt comprendre comment la programmation orientée objet peut nous permettre de construire une meilleure interface pour les utilisateurs de notre librairie.

Nous allons utiliser comme exemple une variable fonctionnelle, c’est-à-dire un ensemble de courbes observées sur une même grille.

8.14 Le modèle mental minimal de S3

Pour comprendre S3, quatre concepts sont particulièrement importants :

objet
classe
générique
méthode

Objet

Un objet contient de l’information.

Par exemple :

x <- c(1, 2, 3)

ou :

fit <- lm(mpg ~ wt + hp, data = mtcars)

sont des objets R.

Cependant, tous les objets R ne participent pas nécessairement à un système de programmation orientée objet.

Classe

Une classe permet d’indiquer à R quel est le type d’objet nous manipulons.

Par exemple :

fit <- lm(mpg ~ wt + hp, data = mtcars)

class(fit)

retourne :

[1] "lm"

R sait donc que fit est un objet représentant un modèle linéaire, idenfité par sa classe; lm.

Dans S3, une classe est essentiellement un attribut ajouté à un objet R.

Nous pouvons voir les attributs d’un objet avec :

attributes(fit)

ou simplement sa classe avec :

class(fit)

Dans le système S3, la classe d’une objet peut-être directement assignée:

class(fit) <- lm

Générique

Une fonction générique représente une opération générale qui peut être utile dans un large éventaille de scénarios.

Par exemple :

print()
plot()
mean()
summary()
predict()

sont des fonctions génériques.

L’idée est qu’une même opération peut avoir un comportement différent selon la classe de l’objet.

Par exemple :

plot(fit)

ne produit pas le même graphique que :

plot(1:10)

même si nous appelons dans les deux cas la fonction :

plot()

Méthode

Une méthode est l’implantation d’une fonction générique pour une classe particulière.

Dans S3, les méthodes suivent généralement la convention :

generique.classe()

Par exemple :

print.lm()
predict.lm()
plot.lm()

sont des méthodes conçues pour les objets de classe "lm".

Lorsque nous écrivons :

plot(fit)

R effectue conceptuellement :

plot(fit)
    ↓
quelle est la classe de fit?
    ↓
"lm"
    ↓
chercher une méthode plot.lm()
    ↓
exécuter plot.lm(fit)

Ce mécanisme s’appelle le method dispatch, ou la répartition des méthodes.

Le cœur de S3

Dans sa forme la plus simple, S3 repose donc sur deux idées :

un objet possède une classe

et :

les fonctions génériques recherchent
des méthodes correspondant à cette classe

C’est simple mais c’est ça!

8.15 Un exemple : une variable fonctionnelle

Supposons que nous observions plusieurs courbes sur une même grille.

Par exemple, générons 30 courbes :

set.seed(123)

grid <- seq(0, 1, length.out = 101)

n <- 30

values <- matrix(
  NA_real_,
  nrow = n,
  ncol = length(grid)
)

for (i in seq_len(n)) {

  amplitude <- rnorm(1, mean = 1, sd = 0.15)
  phase <- rnorm(1, mean = 0, sd = 0.08)

  values[i, ] <-
    amplitude * sin(2 * pi * (grid + phase)) +
    rnorm(length(grid), sd = 0.15)
}

La matrice :

values

contient nos courbes :

lignes    → individus
colonnes  → points de la grille

Nous avons également besoin de conserver :

grid

qui nous indique où les courbes sont observées.

Nous pouvons regrouper ces informations dans une liste :

temperature <- list(
  values = values,
  grid = grid,
  name = "Température"
)

Cette liste contient maintenant tout ce dont nous avons besoin.

Cependant, pour R, elle demeure simplement une liste :

class(temperature)

retourne :

[1] "list"

8.16 Créer notre première classe S3

Nous voulons indiquer à R que cette liste représente quelque chose de plus spécifique qu’une simple liste.

Nous pouvons lui attribuer une classe :

class(temperature) <- "funvar"

Puis :

class(temperature)

retourne :

[1] "funvar"

Nous venons de créer notre premier objet S3.

Une classe S3 est très légère

Nous n’avons pas eu besoin de déclarer formellement la classe "funvar" quelque part.

Cette commande suffit :

class(temperature) <- "funvar"

C’est l’une des grandes forces, mais aussi l’une des faiblesses, de S3 : le système est extrêmement flexible et repose largement sur des conventions généralement respecté par les utilisateurs.

À ce stade, notre objet contient :

names(temperature)

soit :

values
grid
name

Nous pouvons accéder directement à ces composantes :

temperature$values
temperature$grid
temperature$name

Mais l’utilisateur de notre librairie ne devrait pas nécessairement avoir à connaître toute cette structure interne.

C’est ici que les méthodes deviennent intéressantes.

Première méthode : print()

Regardons ce qui se produit actuellement :

temperature

R imprime essentiellement toute la liste.

Dans notre cas, cela signifie potentiellement imprimer une matrice contenant des milliers de valeurs.

Ce n’est probablement pas ce qu’un utilisateur souhaite voir lorsqu’il demande simplement :

temperature

Nous pouvons définir une méthode d’affichage spécifique à notre classe :

print.funvar <- function(x, ...) {

  cat("Variable fonctionnelle\n")
  cat("Nom :", x$name, "\n")
  cat("Nombre de courbes :", nrow(x$values), "\n")
  cat("Nombre de points :", ncol(x$values), "\n")

  cat(
    "Domaine : [",
    min(x$grid),
    ", ",
    max(x$grid),
    "]\n",
    sep = ""
  )

  invisible(x)
}

Nous pouvons maintenant écrire :

print(temperature)

ou simplement :

temperature

et obtenir quelque chose comme :

Variable fonctionnelle
Nom : Température
Nombre de courbes : 30
Nombre de points : 101
Domaine : [0, 1]

Le contenu interne de l’objet n’a pas changé.

Ce qui a changé est la manière dont l’utilisateur interagit avec lui.

Avant :

temperature
    ↓
énorme liste de nombres

Après :

temperature
    ↓
résumé utile de l'objet
Premier bénéfice de la POO

La programmation orientée objet nous permet de séparer :

comment les données sont stockées

de :

comment elles sont présentées à l'utilisateur

Nous pouvons donc modifier la structure interne de notre objet plus tard sans nécessairement modifier l’interface offerte aux utilisateurs.

Deuxième méthode : plot()

Une variable fonctionnelle possède également une représentation graphique naturelle.

Sans programmation orientée objet, l’utilisateur devrait savoir que les courbes se trouvent dans :

temperature$values

et que leur grille se trouve dans :

temperature$grid

Il devrait ensuite écrire quelque chose comme :

matplot(
  temperature$grid,
  t(temperature$values),
  type = "l",
  lty = 1
)

Mais si l’objet représente une variable fonctionnelle, nous pouvons définir directement ce que signifie :

plot(temperature)

Créons une méthode :

plot.funvar <- function(x,
                        show_mean = TRUE,
                        ...) {

  matplot(
    x$grid,
    t(x$values),
    type = "l",
    lty = 1,
    xlab = "t",
    ylab = x$name,
    ...
  )

  if (show_mean) {
    lines(
      x$grid,
      colMeans(x$values),
      lwd = 3
    )
  }

  invisible(x)
}

Nous pouvons maintenant simplement écrire :

plot(temperature)

R effectue alors conceptuellement :

plot(temperature)
       ↓
class(temperature)
       ↓
"funvar"
       ↓
plot.funvar()

Notre méthode affiche toutes les courbes ainsi que leur moyenne.

8.17 Arguments spécifiques et ...

Notre méthode possède deux types d’arguments supplémentaires.

Premièrement :

show_mean = TRUE

est un argument spécifique à notre méthode plot.funvar().

Il permet par exemple :

plot(
  temperature,
  show_mean = FALSE
)

Deuxièmement, nous avons :

...

Les arguments contenus dans ... sont transmis à matplot().

Par exemple :

plot(
  temperature,
  main = "Courbes de température",
  lwd = 2
)

conduit conceptuellement à :

plot(
  temperature,
  main = "...",
  lwd = 2
)
        ↓
plot.funvar(
  temperature,
  main = "...",
  lwd = 2
)
        ↓
matplot(
  ...,
  main = "...",
  lwd = 2
)

Nous avons donc :

show_mean
    ↓
argument propre à plot.funvar()


main, lwd, ...
    ↓
arguments transmis à matplot()

Troisième méthode : mean()

Les méthodes ne servent pas uniquement à modifier l’affichage.

Nous pouvons également définir des opérations statistiques naturelles pour notre classe.

Une variable fonctionnelle composée de plusieurs courbes possède, par exemple, une courbe moyenne.

Définissons :

mean.funvar <- function(x, ...) {

  mean_values <- matrix(
    colMeans(x$values),
    nrow = 1
  )

  result <- list(
    values = mean_values,
    grid = x$grid,
    name = paste("Moyenne de", x$name)
  )

  class(result) <- "funvar"

  result
}

Nous pouvons maintenant calculer :

mean_temperature <- mean(temperature)

Puis :

mean_temperature

et :

plot(mean_temperature)

fonctionnent immédiatement.

Pourquoi?

Parce que mean.funvar() retourne lui-même un nouvel objet de classe :

"funvar"

Ce nouvel objet bénéficie donc automatiquement des méthodes que nous avons déjà écrites :

                   temperature
                       │
                       ▼
                    mean()
                       │
                       ▼
                mean.funvar()
                       │
                       ▼
               nouvel objet funvar
                       │
              ┌────────┴────────┐
              ▼                 ▼
           print()            plot()
Deuxième bénéfice de la POO

En définissant un ensemble cohérent de méthodes, nous construisons progressivement une interface commune pour tous les objets de notre classe.

Une nouvelle fonction qui retourne un objet "funvar" peut automatiquement profiter des méthodes déjà disponibles.

La classe comme contrat implicite

À ce stade, nous supposons qu’un objet "funvar" possède toujours :

values
grid
name

et que :

ncol(values) == length(grid)

Mais S3 ne vérifie pas automatiquement cette structure.

Par exemple, rien ne nous empêche d’écrire :

x <- list(
  pizza = 12
)

class(x) <- "funvar"

R accepte parfaitement cet objet.

Mais :

plot(x)

échouera probablement, puisque plot.funvar() s’attend à trouver :

x$grid
x$values

Nous rencontrons ici une limite importante de S3 :

S3 sait qu’un objet possède une certaine classe, mais ne garantit pas automatiquement que cet objet possède une structure valide.

C’est une des raisons pour lesquelles il est préférable de centraliser la création de nos objets.

8.18 Utiliser un constructeur

Nous avons jusqu’à maintenant créé nos objets avec :

result <- list(...)
class(result) <- "funvar"

Cette approche est parfaite pour comprendre comment S3 fonctionne.

Dans une véritable librairie, nous préférons cependant utiliser une fonction dédiée à la construction des objets.

Par convention, nous pouvons l’appeler :

new_funvar()

Par exemple :

new_funvar <- function(values,
                       grid,
                       name = "Variable fonctionnelle") {

  stopifnot(
    is.matrix(values),
    is.numeric(values),
    is.numeric(grid),
    ncol(values) == length(grid),
    length(name) == 1
  )

  structure(
    list(
      values = values,
      grid = grid,
      name = name
    ),
    class = "funvar"
  )
}

Nous pouvons maintenant construire notre objet avec :

temperature <- new_funvar(
  values = values,
  grid = grid,
  name = "Température"
)

Le constructeur joue donc deux rôles.

Premièrement, il centralise la création de notre objet :

list(...)
+
class(...)

Deuxièmement, il garantit certaines propriétés minimales :

values est une matrice numérique
grid est numérique
ncol(values) == length(grid)
Pourquoi utiliser un constructeur?

Sans constructeur, nous pourrions créer des objets "funvar" à plusieurs endroits différents :

class(x) <- "funvar"

class(y) <- "funvar"

class(z) <- "funvar"

et oublier une composante ou créer une structure légèrement différente.

Avec :

new_funvar()

nous avons un seul endroit qui définit la structure attendue de notre classe.

Modifier mean.funvar()

Maintenant que nous possédons un constructeur, notre méthode :

mean.funvar()

n’a plus besoin de reconstruire manuellement l’objet.

Nous pouvons écrire :

mean.funvar <- function(x, ...) {

  mean_values <- matrix(
    colMeans(x$values),
    nrow = 1
  )

  new_funvar(
    values = mean_values,
    grid = x$grid,
    name = paste("Moyenne de", x$name)
  )
}

Notre architecture devient donc :

new_funvar()
      ↓
définit comment créer
un objet funvar


print.funvar()
plot.funvar()
mean.funvar()
      ↓
définissent comment
utiliser un objet funvar

C’est une distinction particulièrement importante.

Dans le cadre de ce cours et la mise-au-point de librairie, il est possible d’ignorer le constructeur, comme nous savons comment nous-même initialiser une objet de nos classes.

8.19 Dans une librairie R

Dans une librairie, nous placerions normalement ces fonctions dans le dossier :

R/

Par exemple :

R/
├── funvar.R
├── print.R
├── plot.R
└── mean.R

ou simplement dans un seul fichier :

R/funvar.R

pour une petite classe.

Le constructeur peut demeurer une fonction interne :

new_funvar()

Il n’est pas nécessaire que l’utilisateur puisse l’appeler directement.

Les méthodes doivent cependant être enregistrées dans le NAMESPACE.

Avec roxygen2, nous pouvons utiliser :

#' @export
print.funvar <- function(x, ...) {
  ...
}
#' @export
plot.funvar <- function(x, y, ...) {
  ...
}
#' @export
mean.funvar <- function(x, ...) {
  ...
}

Puis :

devtools::document()

générera dans NAMESPACE quelque chose ressemblant à :

S3method(mean,funvar)
S3method(plot,funvar)
S3method(print,funvar)

Nous ne modifions donc pas directement :

NAMESPACE

comme d’habitude.

Le workflow devient :

écrire une méthode
       ↓
ajouter @export
       ↓
devtools::document()
       ↓
méthode enregistrée dans NAMESPACE
       ↓
devtools::load_all()
       ↓
tester la méthode

Par exemple :

devtools::document()
devtools::load_all()

print(temperature)
plot(temperature)
mean(temperature)

8.20 Pourquoi ne pas simplement créer plot_funvar()?

À ce stade, une question raisonnable serait :

Pourquoi utiliser S3? Nous pourrions simplement écrire des fonctions comme plot_funvar() et mean_funvar().

Effectivement, nous pourrions.

Par exemple :

plot_funvar(temperature)

fonctionnerait parfaitement.

Mais l’intérêt de la programmation orientée objet est de fournir une interface commune.

Avec S3 :

plot(x)

signifie :

Trace une représentation appropriée de cet objet.

L’utilisateur n’a pas besoin de mémoriser :

plot_funvar()
plot_lm()
plot_glm()
plot_factor()
...

Il utilise simplement :

plot()

et laisse R choisir la méthode appropriée.

Même chose pour :

print()
mean()
predict()
summary()

Nous obtenons donc une interface beaucoup plus cohérente.

Le véritable intérêt

Le bénéfice principal de S3 n’est pas simplement de pouvoir écrire :

plot.funvar()

Le bénéfice est que l’utilisateur n’a pas besoin de savoir que cette fonction existe.

Il écrit simplement :

plot(x)

et la classe de x détermine le comportement approprié.

8.21 Une courte introduction à l’héritage

Les classes S3 peuvent également avoir plus d’une classe.

Considérons un modèle linéaire généralisé :

fit <- glm(
  am ~ wt + hp,
  data = mtcars,
  family = binomial()
)

class(fit)

retourne :

[1] "glm" "lm"

Cet objet est donc considéré d’abord comme un objet "glm", puis comme un objet "lm".

Lorsqu’une fonction générique est appelée, R cherche les méthodes dans cet ordre.

Conceptuellement :

plot(fit)
    ↓
plot.glm() existe?
    ↓
sinon
    ↓
plot.lm() existe?
    ↓
sinon
    ↓
plot.default()

Cela permet à une classe plus spécialisée de réutiliser des comportements définis pour une classe plus générale.

C’est ce qu’on appelle l’héritage.

Pour cette introduction à S3, nous n’utiliserons pas directement l’héritage dans notre classe funvar.

Il est surtout important de comprendre l’idée :

une classe spécialisée
peut réutiliser les méthodes
d'une classe plus générale

Bien penser une classes veut souvent dire bien considérer la hierarchie d’héritage.

Ce ne sera pas nécessaire dans la câdre de ce cours, mais c’est important de connaître l’existence de ce concept.

Retour sur notre classe funvar

Nous avons commencé avec deux objets indépendants :

values
grid

Puis nous les avons regroupés :

temperature <- list(
  values = values,
  grid = grid,
  name = "Température"
)

Ensuite, nous avons donné un sens conceptuel à cette structure :

class(temperature) <- "funvar"

et défini des comportements naturels :

print(temperature)

plot(temperature)

mean(temperature)

Finalement, nous avons centralisé sa construction :

new_funvar()

Notre architecture complète ressemble donc à :

                     new_funvar()
                          │
                          ▼
                  objet de classe
                      "funvar"
                          │
             ┌────────────┼────────────┐
             ▼            ▼            ▼
          print()       plot()       mean()
             │            │            │
             ▼            ▼            ▼
      print.funvar  plot.funvar  mean.funvar

8.22 Ce que la POO nous apporte

La programmation orientée objet n’a pas nécessairement modifié nos calculs.

Les courbes sont toujours stockées dans une matrice.

La moyenne fonctionnelle est toujours :

colMeans(values)

Ce que la POO a changé est plutôt l’organisation de notre logiciel et l’interface offerte à l’utilisateur.

Sans POO :

matplot(
  grid,
  t(values),
  type = "l"
)

mean_curve <- colMeans(values)

L’utilisateur doit connaître :

  • la structure des données;
  • la signification des lignes et colonnes;
  • la grille associée;
  • la fonction appropriée à utiliser;
  • la manière de reconstruire un objet après une transformation.

Avec S3 :

plot(temperature)

mean_temperature <- mean(temperature)

plot(mean_temperature)

L’utilisateur travaille maintenant avec un objet qui possède une signification statistique et un ensemble de comportements naturels.

Message principal

La programmation orientée objet ne sert pas uniquement à créer des objets plus compliqués.

Elle permet surtout de construire une interface dans laquelle :

les données
+
leur signification
+
les opérations naturelles

forment un ensemble cohérent.

S3 est une manière particulièrement simple d’introduire cette idée dans une librairie R.

8.23 Au-delà de S3 : S4, R6 et S7

S3 nous a permis d’introduire les principales idées de la programmation orientée objet :

classe
   ↓
objet
   ↓
générique
   ↓
méthode

et surtout de construire une interface simple :

print(x)
plot(x)
mean(x)
predict(x)

dont le comportement dépend de la classe de x.

La grande force de S3 est sa simplicité.

Nous avons toutefois également rencontré certaines de ses limites.

Par exemple, rien ne nous empêchait d’écrire :

x <- list(
  pizza = 12
)

class(x) <- "funvar"

R acceptait alors parfaitement cet objet comme étant de classe "funvar".

S3 ne définit donc pas formellement :

  • quelles composantes un objet doit contenir;
  • quel doit être le type de ces composantes;
  • quelles valeurs sont permises;
  • comment l’objet doit être construit.

Nous avons compensé cette faiblesse en écrivant nous-mêmes :

new_funvar()

et en ajoutant certaines vérifications.

D’autres systèmes de programmation orientée objet disponibles dans R proposent des solutions plus formelles à ces problèmes.

Nous allons brièvement considérer :

R6
S4
S7

L’objectif n’est pas de maîtriser ces systèmes, mais plutôt de comprendre ce qu’ils ajoutent à S3 et pourquoi ils existent.

8.24 R6 : changer de paradigme

R6 est assez différent de S3.

Avec S3, nous utilisons principalement une POO fonctionnelle :

plot(x)
mean(x)
predict(x)

Les méthodes appartiennent aux fonctions génériques.

Avec R6, les méthodes appartiennent plutôt directement aux objets.

On utilise alors une syntaxe du type :

x$plot()
x$predict()

On parle de POO encapsulée.

Cette approche ressemble davantage à celle utilisée dans plusieurs autres langages orientés objet, Java par exemple.

Des objets qui peuvent changer

Une deuxième différence importante est que les objets R6 sont mutables.

Considérons conceptuellement un objet :

compteur

contenant une valeur :

0

Une méthode R6 pourrait modifier directement cet objet :

compteur$incrementer()

et la valeur stockée dans compteur serait maintenant différente.

Avec la majorité des objets R traditionnels, nous travaillons plutôt selon une logique de :

objet initial
     ↓
fonction
     ↓
nouvel objet

R6 utilise des sémantiques de référence : plusieurs variables peuvent donc faire référence au même objet, et une modification effectuée à travers l’une d’elles est visible à travers les autres.

Cette propriété est particulièrement utile pour représenter quelque chose qui possède un état qui évolue au cours du temps.

Par exemple :

connexion à une base de données
session web
connexion à une API
état d'une application
ressource externe
Pourquoi ne pas tout faire avec R6?

Les objets mutables peuvent être très pratiques, mais ils rendent également le comportement d’un programme plus difficile à prévoir.

Pour plusieurs objets statistiques, une approche fonctionnelle comme S3 demeure donc plus naturelle :

fit <- lm(...)
prediction <- predict(fit)

plutôt qu’un objet qui modifie constamment son propre état.

Dans ce cours, nous ne développerons pas de classe R6. Il est surtout important de reconnaître qu’il s’agit d’une autre philosophie de programmation orientée objet.

8.25 S4 : rendre S3 plus formel

S4 conserve une philosophie beaucoup plus proche de S3.

Il s’agit toujours principalement de POO fonctionnelle :

generique(objet)

mais la définition des classes est beaucoup plus formelle.

Avec S3, nous avions simplement écrit :

class(temperature) <- "funvar"

Avec S4, nous devons réellement définir la classe.

Par exemple :

methods::setClass(
  "Funvar",
  slots = c(
    values = "matrix",
    grid = "numeric",
    name = "character"
  )
)

Nous indiquons maintenant explicitement que tout objet "Funvar" doit posséder :

values   → matrix
grid     → numeric
name     → character

Les composantes d’un objet S4 sont appelées des slots.

Nous pouvons ensuite construire un objet avec :

temperature <- methods::new(
  "Funvar",
  values = values,
  grid = grid,
  name = "Température"
)

et accéder aux slots avec :

temperature@values
temperature@grid
temperature@name

Validation plus stricte

S4 vérifie automatiquement que les objets stockés dans les slots possèdent le bon type.

Nous pouvons également définir des contraintes supplémentaires.

Par exemple :

methods::setValidity(
  "Funvar",
  function(object) {

    if (ncol(object@values) != length(object@grid)) {
      return(
        "Le nombre de colonnes de `values` doit correspondre à la longueur de `grid`."
      )
    }

    TRUE
  }
)

Nous obtenons donc une distinction importante :

S3
─────────────────────────────
structure implicite
conventions
flexibilité


S4
─────────────────────────────
structure déclarée
types définis
validation formelle

S4 offre également des mécanismes plus avancés, notamment :

  • l’héritage multiple;
  • la définition formelle des génériques;
  • la définition formelle des méthodes;
  • le multiple dispatch, où la méthode choisie peut dépendre de la classe de plusieurs arguments.

Cette rigueur devient particulièrement intéressante dans de grandes architectures comportant plusieurs classes reliées entre elles.

C’est notamment une des raisons pour lesquelles S4 est très présent dans l’écosystème Bioconductor.

Le compromis

S4 apporte davantage de garanties que S3.

En échange, il nécessite davantage de code et possède une mécanique plus complexe.

Pour une petite classe statistique, cette complexité supplémentaire n’est pas toujours nécessaire.

8.26 S7 : une tentative de réunir les forces de S3 et S4

S7 est beaucoup plus récent; toujours en développement!

Il a été conçu par le groupe de travail sur la programmation orientée objet du R Consortium, avec l’objectif explicite de proposer éventuellement un successeur aux systèmes S3 et S4.

S7 conserve une caractéristique importante de S3 :

Il s’agit toujours principalement de POO fonctionnelle.

Nous continuons donc à écrire :

plot(x)
mean(x)
predict(x)

plutôt que :

x.plot()
x.mean()
x.predict()

Mais les classes sont maintenant définies de manière formelle, comme avec S4.

On peut donc voir grossièrement S7 comme une tentative de combiner :

simplicité et interface de S3
              +
structure et garanties de S4

8.27 Définir une classe S7

Avec S7, une classe est elle-même un objet R.

Par exemple :

Funvar <- S7::new_class(
  "Funvar",
  properties = list(
    values = S7::class_any,
    grid = S7::class_numeric,
    name = S7::class_character
  )
)

La classe :

Funvar

est maintenant un objet représentant notre définition de classe.

Elle joue également le rôle de constructeur.

Nous pouvons donc directement écrire :

temperature <- Funvar(
  values = values,
  grid = grid,
  name = "Température"
)

Cela constitue déjà une différence intéressante avec notre implantation S3.

Avec S3, nous avions dû créer nous-mêmes :

new_funvar()

Avec S7, la définition de la classe produit automatiquement un constructeur.

8.28 Les propriétés

Dans S7, les composantes d’un objet sont appelées des propriétés.

Nous y accédons avec :

temperature@values
temperature@grid
temperature@name

Cette notation ressemble à celle des slots S4.

Cependant, les propriétés font partie explicitement de la définition de la classe.

Par exemple :

grid = S7::class_numeric

signifie que la propriété grid doit contenir un objet numérique.

Une tentative comme :

temperature@grid <- "bonjour"

sera donc rejetée automatiquement.

Cela contraste fortement avec S3, où rien n’empêchait un utilisateur d’écrire :

temperature$grid <- "bonjour"

et de rendre notre objet incohérent.

8.29 Ajouter un validateur

Les types ne suffisent pas toujours.

Dans notre variable fonctionnelle, nous voulons également imposer :

nombre de colonnes de values
        =
longueur de grid

Nous pouvons intégrer cette contrainte directement à la définition de la classe :

Funvar <- S7::new_class(
  "Funvar",

  properties = list(
    values = S7::class_any,
    grid = S7::class_numeric,
    name = S7::class_character
  ),

  validator = function(self) {

    if (!is.matrix(self@values)) {
      return("@values doit être une matrice.")
    }

    if (!is.numeric(self@values)) {
      return("@values doit être une matrice numérique.")
    }

    if (ncol(self@values) != length(self@grid)) {
      return(
        "Le nombre de colonnes de @values doit correspondre à la longueur de @grid."
      )
    }

  }
)

La validation est alors associée directement à la classe.

Elle est effectuée lors de la construction de l’objet et lorsque ses propriétés sont modifiées.

Notre définition regroupe donc maintenant :

nom de la classe
      +
propriétés
      +
types
      +
contraintes de validité
      +
constructeur

C’est une différence importante avec S3, où tous ces éléments reposaient principalement sur nos propres conventions.

8.30 Les méthodes avec S7

S7 conserve le principe des fonctions génériques.

Nous pouvons donc encore utiliser un générique existant comme :

plot()

et définir une méthode pour notre classe.

La syntaxe devient cependant explicite :

S7::method(plot, Funvar) <- function(x, y, ...) {

  matplot(
    x@grid,
    t(x@values),
    type = "l",
    lty = 1,
    xlab = "t",
    ylab = x@name,
    ...
  )

  invisible(x)
}

Nous pouvons ensuite écrire exactement comme avec S3 :

plot(temperature)

L’utilisateur n’a donc pas besoin de savoir si notre implantation utilise :

S3
S4
ou
S7

L’interface peut demeurer :

plot(x)

C’est une caractéristique importante de la POO fonctionnelle en R.

8.31 Créer un nouveau générique avec S7

S7 fournit également une manière explicite de créer nos propres fonctions génériques.

Par exemple, imaginons une opération permettant de retourner le nombre de courbes d’un objet :

ncurves <- S7::new_generic(
  "ncurves",
  "x"
)

Nous pouvons ensuite définir une méthode :

S7::method(ncurves, Funvar) <- function(x) {
  nrow(x@values)
}

Puis :

ncurves(temperature)

La relation entre le générique et sa méthode est donc beaucoup plus explicite qu’en S3.

En S3, nous aurions écrit quelque chose comme :

ncurves <- function(x, ...) {
  UseMethod("ncurves")
}

ncurves.funvar <- function(x, ...) {
  nrow(x$values)
}

S7 remplace cette convention de noms par une véritable opération d’enregistrement :

S7::method(ncurves, Funvar) <- ...

8.32 Pourquoi S7 est particulièrement intéressant?

S7 cherche à conserver plusieurs aspects agréables de S3 :

POO fonctionnelle

plot(x)
mean(x)
predict(x)

tout en corrigeant plusieurs de ses faiblesses.

Par exemple :

S3 S7
Classe généralement implicite Classe explicitement définie
Structure basée sur une convention Propriétés déclarées
Types non imposés Types de propriétés vérifiés
Constructeur à créer nous-mêmes Constructeur associé à la classe
Validation à organiser nous-mêmes Validateur intégré à la classe
Méthodes reconnues par convention de nom Méthodes enregistrées explicitement
Héritage basé sur le vecteur class Héritage explicitement défini

S7 ajoute également des mécanismes plus avancés, notamment la possibilité de faire dépendre la sélection d’une méthode de plusieurs arguments, tout en conservant une logique de programmation fonctionnelle.

L’idée derrière S7

S7 ne cherche donc pas à remplacer la philosophie de S3.

Il cherche plutôt à conserver son interface simple :

generique(objet)

tout en ajoutant davantage de structure et de garanties pour le développement de librairies complexes.

8.33 S7 est encore récent

S7 est disponible sur CRAN, mais il demeure un système beaucoup plus récent que S3 ou S4.

Son utilisation dans l’écosystème R est donc encore relativement limitée.

Le projet indique d’ailleurs toujours que S7 possède un caractère expérimental, même si sa conception est maintenant suffisamment avancée pour être utilisée et expérimentée.

L’objectif à long terme annoncé par le projet est que S7 puisse éventuellement être intégré directement à R.

Pour cette raison, il est important aujourd’hui :

  • de connaître son existence;
  • de comprendre sa philosophie;
  • de pouvoir lire du code S7;

mais nous n’allons pas remplacer S3 par S7 dans notre projet.

8.34 Quel système choisir?

Nous pouvons maintenant résumer grossièrement les différents systèmes :

Système Philosophie Principal avantage
S3 POO fonctionnelle Simplicité et flexibilité
R6 POO encapsulée Objets mutables et état
S4 POO fonctionnelle formelle Contrôle et rigueur
S7 POO fonctionnelle formelle Cherche à combiner simplicité et rigueur

Pour une petite librairie statistique :

S3

demeure souvent un excellent point de départ.

Pour une architecture très structurée comprenant plusieurs classes et plusieurs développeurs :

S4

peut fournir davantage de garanties.

Pour représenter des objets possédant un état mutable ou des ressources externes :

R6

peut être particulièrement naturel.

Et :

S7

propose une nouvelle approche qui cherche à conserver l’interface naturelle de S3 tout en intégrant plusieurs mécanismes formels que nous retrouvons dans S4.

Message à retenir

Il n’existe pas un système de POO universellement supérieur.

Les différents systèmes répondent à des compromis différents entre :

simplicité
flexibilité
rigueur
encapsulation
maintenabilité

Dans ce cours, S3 demeure notre outil principal parce qu’il permet de profiter rapidement des bénéfices de la programmation orientée objet tout en conservant une implantation relativement simple.
