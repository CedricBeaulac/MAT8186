2  Projet R

Avant d’introduire GitHub et la publication en ligne de notre librairie, discutons rapidement d’un outil qui nous sera très utile pour organiser notre travail : le projet RStudio.

2.1 Le problème

On commence souvent un projet en définissant manuellement notre répertoire de travail :

setwd("C:/Users/MYPC/Desktop/MAT8186")

Ça fonctionne très bien… sur mon ordinateur!

Le problème apparaît rapidement lorsque :

  • le projet est déplacé vers un autre répertoire;
  • le projet est synchronisé avec un service infonuagique;
  • le projet est partagé avec un collègue;
  • le projet est téléchargé sur un autre ordinateur.

Par exemple, le chemin

C:/Users/MYPC/Desktop/MAT8186

n’existe probablement pas sur votre ordinateur.

On aimerait donc que notre code puisse fonctionner indépendamment de l’endroit où le projet est enregistré.

Un principe important

Notre code ne devrait pas dépendre de l’emplacement exact du projet sur notre ordinateur.

2.2 Le projet RStudio

Un projet RStudio permet de regrouper dans un même répertoire tout ce qui est associé à une tâche :

mon_projet/
├── mon_projet.Rproj
├── R/
├── data/
├── figures/
└── notes.qmd

Le fichier .Rproj identifie ce répertoire comme un projet RStudio.

Lorsque nous ouvrons ce fichier, RStudio ouvre le projet et utilise automatiquement la racine du projet comme répertoire de travail.

Autrement dit, si notre projet est :

C:/Users/MYPC/Desktop/MAT8186/

alors :

getwd()

retournera quelque chose comme :

C:/Users/MYPC/Desktop/MAT8186

Mais si un autre utilisateur place exactement le même projet dans :

C:/Users/YOURPC/Documents/MAT8186/

la racine de son projet sera automatiquement :

C:/Users/YOURPC/Documents/MAT8186

Il n’est donc plus nécessaire d’écrire un setwd() spécifique à chaque ordinateur.

Les chemins relatifs

C’est ici qu’apparaît l’un des principaux avantages du projet.

Supposons que notre structure soit :

MAT8186/
├── MAT8186.Rproj
├── data/
│   └── donnees.csv
├── R/
│   └── analyse.R
└── notes.qmd

Plutôt que d’écrire :

read.csv(
  "C:/Users/MYPC/Desktop/MAT8186/data/donnees.csv"
)

nous pouvons simplement écrire :

read.csv("data/donnees.csv")

Le chemin est maintenant relatif à la racine du projet.

Si nous déplaçons tout le projet ailleurs, le chemin

data/donnees.csv

demeure valide.

Il fonctionnera également sur l’ordinateur d’un collègue qui possède la même structure de projet.

Une bonne règle

Si votre code contient :

setwd("C:/Users/mon_nom/...")

ou un autre chemin propre à votre ordinateur, demandez-vous s’il ne serait pas préférable de travailler à partir d’un projet et d’utiliser un chemin relatif.

2.3 Partir à neuf

R et RStudio peuvent conserver automatiquement une partie de notre environnement de travail entre deux sessions.

Deux fichiers que vous avez peut-être déjà rencontrés sont :

.RData
.Rhistory

.RData peut contenir les objets présents dans notre environnement R à la fin d’une session, tandis que .Rhistory peut conserver l’historique des commandes exécutées.

Cela peut sembler pratique.

Cependant, dans un projet reproductible, nous voulons idéalement être capables de reconstruire notre environnement à partir de notre code.

Par exemple, si notre analyse nécessite l’objet donnees, nous préférons avoir :

donnees <- read.csv("data/donnees.csv")

dans notre code plutôt que de dépendre d’un objet donnees qui serait mystérieusement réapparu depuis une ancienne session R.

L’idée est donc de travailler avec intention : les objets nécessaires à notre analyse devraient pouvoir être recréés à partir des fichiers et du code contenus dans notre projet.

Pour cette raison, il est généralement recommandé de ne pas restaurer automatiquement .RData au démarrage et de ne pas sauvegarder automatiquement l’environnement de travail à la fermeture de RStudio.

Nous pouvons configurer ce comportement dans :

Tools -> Global Options -> General

et choisir notamment :

Restore .RData into workspace at startup : NON

Save workspace to .RData on exit : Never
Reproductibilité

Une bonne question à se poser est :

Si je ferme complètement RStudio, que je rouvre mon projet et que je réexécute mon code, est-ce que je peux reproduire mes résultats?

Si la réponse est oui, nous sommes sur la bonne voie.

2.4 Créer un projet

Lorsque nous commençons sérieusement une nouvelle tâche – une analyse de données, la rédaction de notes Quarto ou le développement d’une librairie – nous pouvons créer un projet avec :

File -> New Project

RStudio nous offre notamment trois possibilités :

New Directory
Existing Directory
Version Control

Nous pouvons donc :

  • créer simultanément un nouveau répertoire et un nouveau projet;
  • transformer un répertoire existant en projet RStudio;
  • récupérer un projet existant à partir d’un dépôt Git.

Lors de la création du projet, RStudio crée notamment un fichier :

nom_du_projet.Rproj

Par la suite, lorsque nous voulons travailler sur ce projet, nous ouvrons le projet lui-même plutôt que d’ouvrir RStudio puis de chercher nos fichiers.

Nous obtenons ainsi un environnement de travail bien délimité :

Projet A
├── données
├── code
├── résultats
└── environnement de travail

Projet B
├── données
├── code
├── résultats
└── environnement de travail

Les différents projets demeurent ainsi bien séparés les uns des autres.

Et notre librairie?

Nous avons en fait déjà utilisé un projet RStudio!

Lorsque nous avons créé notre librairie avec :

usethis::create_package("mat8186demo")

nous avons obtenu quelque chose comme :

mat8186demo/
├── mat8186demo.Rproj
├── DESCRIPTION
├── NAMESPACE
└── R/

Notre librairie est donc également un projet RStudio.

Et lors de notre survol du développement d’une librairie, nous avons ajouté :

usethis::use_git()

Notre même répertoire est maintenant :

un répertoire
      +
un projet RStudio
      +
une librairie R
      +
un dépôt Git

Il nous reste maintenant à comprendre un peu mieux ce dernier élément.
